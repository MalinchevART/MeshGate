# T2 Вариант 3 — „Изцяло inline, без нови файлове"

## Какво съдържа

| Файл | Къде се приема (copy/paste) | Какво прави |
|---|---|---|
| `topbar-fragment.tsx` | `apps/web/src/App.tsx` ~ред 116–119 (топбар `.brand`) | inline `<svg>` на символа (24px) + `Mesh` + `Gate` през `<span style={{color:'var(--accent-primary)'}}>` |
| `login-fragment.tsx` | `apps/web/src/App.tsx` ~ред 211–212 (`<h1>` + `<p>` в Login) | символ на 40px + Mesh/Gate + таглайн `MONITOR / MANAGE / CONNECT` (моно, fs-12, letter-spacing 2.2, `--text-muted`) |
| `favicon-datauri.html` | `apps/web/index.html` → `<head>` | `<link rel="icon" href="data:image/svg+xml,…">` (864 символа, минимизиран, `%23`/`%3C`/`%3E`/`%22`/`%20`) + `<meta name="theme-color" content="#07131F">` |

Символът е 1:1 спрямо спесификацията (два триъгълника stroke 12, вътрешни
връзки stroke 4 от реле-възела, 5 възли), с tight `viewBox="29 40 180 133"`
(граници, вкл. половините щрихове и радиусите: x 29–209, y 40–173). За
favicon кадърът е разширен до квадрат `25 12 188 188`, за да пълни 16×16 tab-а.

**Вердикт по въпроса „.brand покрива ли текста?"** — да, за layout-а: flex/gap/
fs-16/fw-semibold/letter-spacing вече са там и нула нов CSS е нужен. Но
`.brand-mark` оцветяваше само глифа `◈`, а не част от думата → затова за
двуцветния wordmark трябва новият `<span>` около „Gate" (inline style, без
промяна на styles.css).

## Плюсове

- **Нула нови файлове в `src/` и `public/`** — приемането е три paste-а в
  два съществуващи файла (`App.tsx`, `index.html`); никакъв build config,
  никакво `vite-plugin-*`, никакви импорти.
- **Нула заявка за favicon** — днес `index.html` няма icon и браузърът намира
  `/favicon.ico` → 404 на всяко първо отваряне; data-URI-то е „безплатно".
- **Всичко на едно място** — топбар-брандът живее точно в топбар JSX-а,
  favicon-ът точно в `index.html`; никакво прескачане между файлове при четене.
- **Favicon-ът е винаги синхронен с кода** — идва от същите path данни
  (буквално), не е отделен актив, който може да застарее.
- Favicon-ът пътува с кеширания HTML → при вътрешни мрежи/лаборатории без
  интернет няма dangling заявка.

## Минуси

- **Дублиране на SVG пътища на 2 места в `App.tsx`** (топбар + Login) —
  ~15 реда × 2; при бъбеща промяна на логото се редактират 2 + 1 (favicon)
  = 3 места, без компилатор/линтер да гъкне при разминаване.
- **Data-URI favicon-ът не се кешира отделно** — 864 символа пътуват с всеки
  HTML документ (Vite не го минифицира, той е литерален атрибут); при чест
  зареждане това е повече байтове по мрежата от отделен кеширан `.svg`.
- **Дълъг, шумен `<head>`** — редът с `href` е непрочетаем на пръв поглед и
  внася URL-encoded blob в иначе минималния `index.html`.
- **Съвместимост**: SVG favicons с data-URI се „мажат" от някои Laravel/PWA
  toolchains и от по-стари Safari (pre-2020), а manifest generators
  (`vite-plugin-pwa`) очакват реален файл; при T7+ PWA офлайн ще се наложи
  файл все пак.
- **По-трудно преизползване от T6 шел-а** — ако приложението се разпадне на
  шел + страници (T6), бранд-блокът няма къде да „живее" споделено: или се
  третира като трети+четвърти copy, или се извлича компонент — т.е. вариант 3
  само отлага (и утежнява) прехода към „файл + компонент".
- Debug/promo нужди (OG image, PNG favicon fallback, Apple touch icon) пак
  изискват файлове — inline подходът покрива само SVG-способните браузъри.

## Сравнение с „файл + компонент" (вариант 1/2 стил)

| Критерий | Вариант 3 (inline) | Файл + компонент |
|---|---|---|
| Файлове в src/public | 0 | 2–3 (`Logo.tsx`, `public/favicon.svg`) |
| Favicon мрежова заявка | 0 (в HTML) | 1, кеширана отделно (immutable hash при build) |
| HTML overhead | +864 символа на зареждане | 0 |
| Sync топбар ↔ Login ↔ favicon | ръчно, 3 копия | едно място (компонент + генериран/копиран svg) |
| T6 шел преизползване | copy-paste на трето място | импорт |
| PWA/manifest/OG разширение | не пасва | естествено |
| Diff noise при ребрандиране | 3 файла | 1–2 файла |

**Извод:** вариант 3 печели като *first move с нула триене* — днес, с два
бранд-сайта (топбар + Login) и без PWA, разходът е минимален и kill-ва 404-та
на favicon веднага. Той губи стратегически: при T6 (шел) и T7+ (PWA/OG)
дублираните пътища и некешираният favicon стават технически дълг, който се
погасява точно с „файл + компонент". Препоръка: приемливо като първи ход
сега — но при първото трето място за логото (T6), мигрирай към споделен компонент.
