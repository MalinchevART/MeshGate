# ADR-004: Автоматизация — Node-RED през Admin API, вграден с отделна автентикация

- Статус: Прието (реализация от Фаза 4)
- Дата: 2026-10-12

## Контекст

Спецификацията изисква визуална автоматизация, но собственият визуален редактор е
голяма и ненужна инвестиция — Node-RED (Apache 2.0) е зрял и с документиран Admin API
за управление на flows. Едновременно с това alerts/rules в Core API са нужни по-рано
(Фаза 1–2), без визуален редактор.

## Решение

1. **Node-RED контейнер** се добавя във Фаза 4, изцяло вътрешен (порт 1880 не се
   публикува). Достъпът е през Traefik на `/nodered` със **собствена автентикация**
   (Node-RED adminAuth) — MeshGate не прокарва своята сесия като автентикация на
   Node-RED и не proxy-ва неговия Admin API без RBAC проверка.
2. Core API управлява Node-RED през **Admin HTTP API** (deploy на flows, списък,
   състояние): патент на интеграцията е в `apps/api/integrations/nodered.py`.
3. В UI: линк/iframe до редактора (ясно маркиран като отделен компонент с отделен
   вход) + връщане към MeshGate Automation страницата с данни от Admin API
   (инстанция жива ли е, брой flows, последен deploy).
4. **Лек rules/alert engine в Core API** (без визуален редактор) отговаря за аларми
   по събития (Фаза 1–2): IF–THEN върху normalized events → запис в `alerts`,
   опционално MQTT/webhook действие. Визуалната автоматизация остава в Node-RED.
5. Home Assistant/Zigbee2MQTT (Фаза 4+): HA MQTT Discovery payload-и се публикуват от
   integration адаптер към EMQX; MeshGate не пресъздава HA функционалност.

## Последствия

- (+) Без дублиране на редактор; автентикационните граници остават ясни.
- (+) Провал на Node-RED не спира останалата платформа (explicit state на интеграцията).
- (−) Две автентикации за потребителя при влизане в редактора — приемливо, изрично
  по спецификация ("preserving its authentication boundaries").
